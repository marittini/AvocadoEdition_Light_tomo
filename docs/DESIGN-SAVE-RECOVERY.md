# 디자인 저장의 실패 복구와 동시 저장 제어

이 기능은 기존 MyISAM 테이블을 유지하며 디자인 설정·웹폰트·추가 코드·생성 CSS를 함께 복구한다. InnoDB로의 강제 변환이나 새 DB 필드는 없다. DB와 파일시스템이 완전한 단일 ACID 트랜잭션이 된다는 뜻은 아니다.

## 저장 흐름

1. 디자인 폼은 표시한 설정의 revision을 함께 보낸다. 다른 탭/세션이 먼저 저장했다면409로 거부하고 입력을 유지한다.
2. 파일 잠금과 DB의 CSS/설정 테이블 쓰기 잠금을 획득한다. 기존 미완료 기록이 있으면 먼저 복구한다.
3. 최신 값과 revision을 비교하고, 후보 설정·폰트·업로드를 검증한다. 업로드는 기존 파일과 다른 고유한 이름으로 저장한다.
4. DB를 바꾸기 전에 후보 값으로 CSS를 생성하고 임시 파일에 쓰기·flush/fsync·권한 설정을 완료한다.
5. 이전 디자인 행·디자인 소유 설정 필드·기존 CSS 바이트·새 파일 목록을 복구 기록에 원자적으로 저장한다.
6. DB 변경 후 다시 읽어 저장값이 후보와 같은지 확인한다. CSS를 같은 디렉터리 내 rename으로 교체하고 완료 기록을 남긴다.
7. 확정 revision·폰트 ID·업로드 경로를 폼에 돌려주고 잠금을 해제한다.

정상적으로 잡을 수 있는 예외는 즉시 이전 DB/CSS로 복원한다. 실패한 저장에서 새로 만든 파일만 정리하며, 기존 파일과 이전 성공 저장의 이미지는 자동 삭제하지 않는다. 기존 사용자 스킨이 오래된 이미지 URL을 참조할 수도 있기 때문이다.

## 프로세스 중단과 다음 요청

복구 기록은 `data/css/.tomo-design/recovery.php`에 보관한다. 디렉터리는0700, 기록은0600이며 PHP 종료문·주석 안의 인코딩된 데이터와 접근 거부 규칙으로 HTTP 노출을 방지한다. 기록에는 디자인 설정 백업이 있으므로 공개하거나 임의로 편집하지 않는다.

`common.php`는 설정을 읽기 전에 미완료 기록을 확인한다. 저장 중단으로 남은 준비 상태는 이전 값으로 복원하고, 완료 상태는 파일·DB revision을 검증한 뒤 기록만 정리한다. 반복 복구도 같은 결과를 낸다.

복구에 필요한 파일/DB 접근이 막혀 있거나 기록을 읽을 수 없으면503으로 중단한다. 비동기 저장 요청에는 같은 의미의 JSON 오류를 보낸다. 저장 완료 뒤 외부에서 디자인 값/파일이 달라졌다면 예전 값으로 강제 덮어쓰지 않고 점검을 요구한다.

## 호스팅 요구사항과 업데이트

- DB 계정에 기존 SELECT/INSERT/UPDATE/DELETE/ALTER와 함께 **LOCK TABLES** 권한이 필요하다. 권한이 없으면 저장 전에 실패하며 기존 값은 바꾸지 않는다.
- PHP가 `data/css`, `data/site`와 비공개 복구 폴더에 쓸 수 있어야 한다. 안정적인 `flock`과 같은 파일시스템 내 원자적 rename을 지원하는 저장소를 사용한다.
- 배포 전 프로그램·파일·DB를 함께 백업하고, 관련 요청의 쓰기를 잠시 중지한다. 프로그램과 `common.php`·폼·저장 모듈을 같은 버전으로 배포한다. 배포 전에 열어둔 폼은 새로고침한다.
- 미완료 기록이 있으면 DB 스키마/엔진을 변경하거나 프로그램을 이전 버전으로 내리기 전에 먼저 복구를 완료한다.

## 오류 대응

1. 브라우저의 실패 메시지가 나오면 입력을 복사해 보관하고 폴더 쓰기 권한·디스크 여유·DB 연결 및 권한을 확인한다.
2.503이면 미완료 복구가 보류된 상태다. 원인을 복원하고 다시 접속하면 재시도한다. **기록만 삭제해 강제로 페이지를 열지 않는다.**
3. 기록 손상이나 저장 완료 후 외부 변경으로 자동 확인이 불가능하면 파일·DB 백업과 기록을 비교해 동일한 시점으로 수동 복원한다. 운영 자료를 공개 채널에 올리지 않는다.

테이블 잠금을 사용하는 동안 관련 DB 읽기는 잠깐 대기할 수 있다. 파일 잠금 대기는 최대5초이며, 오래된 폼은 자동 병합하지 않는다. 디스크/서버의 전원 장애와 임의의 FTP·직접 SQL 변경, 별도 서버의 독립 데이터 폴더까지 분산 트랜잭션으로 보장하지는 않는다. 이미 실행 중인 HTTP 문서와 CSS 요청의 전환 시점까지 한 순간으로 만드는 것도 아니다.

복구 기록 생성 이전에 프로세스가 종료되면 DB는 변경되지 않지만 미참조 임시 파일이 남을 수 있다. 성공 이전 이미지도 보존하므로 용량 정리는 참조 관계와 백업을 확인한 뒤 별도로 수행한다.

## 검증

- 실제 DB의 별도 테이블과 임시 폴더에서6개 저장 단계 강제 실패, 실제 MyISAM SQL 오류, 일반 사용자 권한의 쓰기 실패를 검증했다.
-5개 단계에서 PHP 프로세스를 종료하고 새 프로세스로 복구했다. 완료 전에는 DB·CSS를 원래대로 복원하고, 완료 후에는 새 상태를 보존했다.
- 두 PHP/DB 세션의 동시 저장에서 한 쪽만 반영되고 나머지는 오래된 revision으로 거부됐다.
- 추가 사용자 컬럼·생성 컬럼·기존 이미지 보존, InnoDB 설치 호환성을 확인했다.
- 실제 HTTP에서 두 탭 충돌, 렌더 실패, CSS 경로 오류, 업로드 보존 및 재시도를 확인했다. 실제 `common.php`의 다음 요청 복구, 복구 불가 시503/JSON, 권한/경로 복구 후 재시도도 확인했다.

```sh
# 격리된 테스트 DB에 임시 일반 테이블을 만들고 삭제하는 CLI 검사
TEST_DB_HOST=... MARIADB_DATABASE=... MARIADB_USER=... MARIADB_PASSWORD=... php tests/design_store_test.php

# 설치된 일회용 사이트의 설정을 실제로 변경하는 브라우저 검사
TEST_URL=... TEST_USER=... TEST_PASSWORD=... TEST_IMAGE=... node tests/design_save_smoke.cjs
```

`TEST_LOCAL_DESIGN_DATA`를 지정하면 로컬 테스트 사이트에서 CSS 경로를 임시로 막는 파일시스템 검사를 추가한다. 해당 데이터 폴더를 소유한 사용자로 실행한다.

`tests/design_recovery_fixture.php`는 **설치된 일회용 사이트를 의도적으로 중단시키는** CLI fixture다. `TEST_ALLOW_DESIGN_INTERRUPT=1` 및 이름에 `test`가 들어간 DB에서만 실행되며 운영 서버에서는 사용하지 않는다. `interrupt`는 종료코드91과 미완료 기록을 남긴다. 이어서 실제 사이트에 요청해 자동 복구를 확인한다. `state`는 비교용 revision/CSS 해시만 출력한다.
